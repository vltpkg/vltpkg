# Scaffold a vlt Docs Page

Create a new page under `www/docs/src/content/docs/` as **MDX** with
Starlight conventions. Three formats, picked by what the reader needs:

- **Lesson** — a learning experience, reader at _study_. Full
  walkthrough ending in a working result. Use for onboarding: publish
  your first package, set up your first monorepo.
- **Task guide** — reader at _work_, already competent. One goal, no
  teaching. Use for "how do I…" recipes. This is what the **Guides**
  section holds.
- **Reference** — lookup, not a narrative. Use for command docs.

Modeled on the [Diátaxis taxonomy](https://diataxis.fr) and the
information architecture of peer package managers/registries (uv,
pnpm, JSR) — see [rationale](references/rationale.md).

## Decide the format

| User intent                                         | Format                                                                    | Location                 |
| --------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------ |
| "Walkthrough / tutorial / first time doing X"       | Lesson                                                                    | `guides/<slug>.mdx`      |
| "How do I do X?" / short recipe for a specific task | Task guide                                                                | `guides/<slug>.mdx`      |
| "Document the `vlt <cmd>` command"                  | Reference                                                                 | `cli/commands/<cmd>.mdx` |
| "Explain <concept>"                                 | Point at reference/concepts pages; write a guide only if it's a real task | —                        |

Scaffold a single page first; only build a folder + `index.mdx` card
grid when the request is for a section of several pages.

## vlt-first commands

When working inside vlt repos, write commands from the vlt family —
`vlt` (package manager + registry CLI), `vlr` (repo task runner), or
`vlx` (exec tool) — never npm or another package manager's commands. A
guide that says `npm publish` teaches the wrong tool.

Exception: docs about **using the registry without changing the user's
package manager** — the **Consumption** category, where showing how
npm/pnpm/yarn/bun/deno point at a vlt scope or mirror is the whole
point. There the user's package manager commands are correct, and
`vlt` must still be the first tab.

Check the real flags in `cli/commands/<cmd>.mdx` before writing —
don't invent options.

## Registry-specific guide categories

vlt is a registry, not just a runtime — its guides cluster around the
jobs a registry does, not language features. Categorize guides toward
these (uv/JSR show the same shape):

- **Publishing** — sign up → scope → token → publish → verify; also CI
  publishing, OIDC, tags.
- **Authentication & access** — tokens, scopes, org membership,
  `vlt login`, `vlt whoami`.
- **Consumption** — pointing vlt _and_ npm/pnpm/yarn/bun/deno at a
  private scope or mirror.
- **Integrations / CI** — GitHub Actions, migrations from npm/pnpm/
  yarn, mirrors.

## File naming & frontmatter

- Slug: kebab-case, task-oriented, no dates —
  `guides/publish-your-first-package.mdx`, `guides/publish-in-ci.mdx`.
- Frontmatter (all pages):

  ```mdx
  ---
  title: Page Title
  sidebar:
    label: Short Label
    order: 0
  ---
  ```

- `order` controls position within the section; omit for command pages
  under an autogenerated group (sorted by name).

## MDX conventions (from `www/docs`)

Import only what you use, from `@astrojs/starlight/components`:

- Terminal commands:

  ```mdx
  import { Code } from '@astrojs/starlight/components'

  <Code code="$ vlt publish --tag=beta" title="Terminal" lang="bash" />
  ```

- Multi-package-manager blocks use `<Tabs syncKey="pkg-manager">` +
  `<TabItem label="vlt|npm|pnpm|yarn|bun|deno">` (see
  `registry/index.mdx`). Sync key must match so tabs stay in sync
  across pages.
- Numbered lessons use `<Steps>` (content must be a single ordered
  list — see `scripts/lint-mdx.mts`).
- Inline callouts: `<Badge text="Note" variant="tip" />`,
  `<Badge text="Caution" variant="caution" />`.
- Callouts / warnings: `:::note` / `:::caution` / `:::tip` (content
  must start on the line **after** the `:::` — collapsed directives
  fail lint).
- Section index pages use `<CardGrid>` +
  `<LinkCard title=… description=… href=… />`.
- Internal links are absolute paths with no trailing slash and **no
  `.mdx`**: `/cli/commands/publish`, `/cli/auth#oidc-openid-connect`.

## Lesson (Diátaxis tutorial style)

A lesson is a _learning experience_, not a task runbook. The reader
follows it once, to acquire familiarity. Structure:

1. **State where you're going** — not "in this tutorial you will
   learn…" but _"We'll publish a private scoped package and install it
   back into another project."_ One or two sentences.
2. **Before you begin** — prerequisites as a checklist: account,
   login, registry scope, tool versions, anything paid.
3. **Steps** — short `##` sections, one action each, in a managed
   single-line path. Ignore options and alternatives; defer them with
   a link.

Lesson-specific rules (this is what makes it engaging):

- **Visible result after every step.** Each step must produce
  something the reader can _see_ — a file created, a command output, a
  dashboard change. If a step produces nothing observable, merge it or
  give it an observation.
- **Narrate the expected output.** After a command: _"The output
  should look something like…"_ with actual output. If a likely
  failure mode exists: _"If you don't see X, you probably forgot to
  Y."_
- **Point out what to notice.** _"Notice the prompt now shows the
  `@acme` scope."_
- **Ruthlessly minimize explanation.** One line of "why" per step at
  most, then link to the concepts/reference page. Explanation
  distracts from doing.
- **End by describing the result.** _"You've now published
  `@acme/utils` to your private registry and installed it back into
  your app."_
- **vlt-family commands only** — the reader learns vlt.
- **Be concrete and reliable.** One specific path, no forks. The
  reader must get the promised result every time.

## Task guide (bun.com/docs/guides style)

A task guide serves the already-competent user at work: one goal, no
teaching. Structure:

1. One-paragraph intro naming the goal ("This guide shows you how to
   publish a package in CI").
2. **Steps** — short sections, one action each, conditional form where
   needed ("if you use pnpm, run…").
3. Optional **Next steps** tail linking 1–2 adjacent pages.

Rules:

- Code-first: put the command before the explanation.
- One goal per page. If a second task appears, link to it instead.
- No digression, explanation, or teaching. If background matters, link
  to it.
- **vlt-family commands only** — `vlt`, `vlr`, `vlx`.
- Keep it scannable: ≤ ~10 short sections, 1–3 line paragraphs.

## Reference page (Deno CLI style)

For `cli/commands/<cmd>.mdx` or a registry feature page. Structure:

1. `title: vlt <cmd>` + `sidebar: { label: <cmd> }`.
2. **Usage** line:

   ```mdx
   <Code code="$ vlt <cmd> [options] [args]" title="Terminal" lang="bash" />
   ```

3. One short paragraph on what it does.
4. **Options** — one `### <flag>` subsection per option, each with a
   terminal example and one-line description. Group related options
   (e.g. auth, CI) under `##` sections when many.
5. **Examples** — realistic end-to-end blocks, including a CI snippet
   where relevant (OIDC, `VLT_TOKEN`).

Verify every flag against `cli/commands/<cmd>.mdx` before writing —
the existing command docs are the source of truth.

## Sidebar wiring (read this — easy to get wrong)

`astro.config.mts` sidebar groups take `autogenerate` **or** explicit
`items`, never both. To add a brand-new top-level section (e.g.
`Guides`), add a group to the `sidebar` array in
`www/docs/astro.config.mts`:

```ts
{
  label: 'Guides',
  collapsed: true,
  autogenerate: { directory: 'guides' },
},
```

With `autogenerate`, a directory's order = min of its children's, so
groups can sort above intro pages — set `sidebar.order` explicitly on
the `index.mdx` to fix ordering.

## Verify (run in `www/docs`)

```bash
vlr lint:mdx            # structural MDX checks (Steps/asides)
vlr lint:check          # eslint (strict typescript-eslint)
vlr format:check        # prettier
vlr posttest            # astro check (type-checks all ts/mts + mdx)
```

Never leave a `href=""` or a link that 404s —
`starlightLinksValidator` fails the build on broken internal links. If
you touch a `.mts` script, it must be fully typed (untyped scripts
fail `astro check` + root eslint).

## Scaffold template (lesson)

```mdx
---
title: <Result you'll produce>
sidebar:
  label: <Short Label>
  order: 0
---

import { Code, Steps, Badge } from '@astrojs/starlight/components'

We'll <accomplish one concrete thing>. Along the way we'll meet

<the key tools/concepts>.

## Before you begin

- [ ] <prerequisite>
- [ ] <prerequisite>

<Steps>
1. **<First action>**

   <Code code="$ vlt …" title="Terminal" lang="bash" />

The output should look something like …

</Steps>

You've now <restate the result>.
```

## Scaffold template (task guide)

```mdx
---
title: <Task outcome>
sidebar:
  label: <Short Label>
  order: 0
---

import { Code, Steps } from '@astrojs/starlight/components'

This guide shows you how to <one specific task>.

<Steps>
1. **<First action>** — <command-first, one line>
2. **<Second action>** — <command-first, one line>
</Steps>
```

For each step, add a
`<Code code="$ vlt …" title="Terminal" lang="bash" />` line under its
list item. Fill the template, then run the four verify commands above.
