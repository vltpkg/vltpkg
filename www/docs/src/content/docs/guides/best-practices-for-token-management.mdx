Service tokens are credentials that grant access to the vlt registry
from automated systems like CI/CD pipelines. Unlike personal tokens
tied to a user, service tokens belong to your account and are designed
for secure, unattended authentication. This guide covers how to
create, use, and manage service tokens securely.

## Token types

vlt supports two kinds of tokens:

- **Personal tokens** are tied to your user account. They carry your
  full account privileges and are subject to two-factor authentication
  (OTP) prompts. Use personal tokens for local development and manual
  operations.
- **Service tokens** belong to your account, not a person. They are
  designed for CI/CD automation and are not subject to OTP
  requirements. Only account owners and admins can create service
  tokens.

All tokens start with the `vlt_1_` prefix and are stored as hashes —
the full value is displayed only once at creation.

## Creating a service token

Service tokens are created and managed in your vlt.io account
dashboard.

<Steps>

1. Go to [vlt.io](https://www.vlt.io/) and sign in to your account.

2. Navigate to **Account Settings** → **Tokens**.

3. Click **Create Token**.

4. Configure the token:
   - **Name**: Give it a descriptive name (e.g.,
     `github-actions-publish`).
   - **Description** (optional): Add context about its intended use.
   - **Privileges**: Select the minimum permissions needed:
     - `package:read` — for installing packages
     - `package:write` — for publishing packages
     - `member:read` — for reading account members
   - **Expiration**: Set an expiration date (recommended: 90 days for
     high-privilege tokens, 1 year for read-only).

5. Click **Generate**.

6. **Copy the token immediately** — it's shown only once. Store it
   securely before closing the dialog.

</Steps>

<Aside type="caution">
  The token value is never shown again after creation. If you lose it,
  you must revoke this token and create a new one.
</Aside>

## Storing tokens securely

### In GitHub Actions

Store your service token as a GitHub Actions secret:

<Steps>

1. Go to your repository on GitHub.

2. Navigate to **Settings** → **Secrets and variables** → **Actions**.

3. Click **New repository secret**.

4. Name it `VLT_PUBLISH_TOKEN` (or a name matching your use case).

5. Paste the token value you copied from vlt.io.

6. Click **Add secret**.

</Steps>

<Aside type="tip">
  For organization-wide tokens, store them as organization secrets
  instead of repository secrets. This reduces the number of separate
  token copies you need to manage.
</Aside>

### In other CI/CD systems

Store tokens using your CI/CD platform's native secret management:

- **GitLab CI**: CI/CD Variables (Settings → CI/CD → Variables)
- **CircleCI**: Context Secrets (Organization → Contexts)
- **Jenkins**: Credentials Store
- **Other systems**: Use environment-specific secret storage, never
  commit tokens to version control

## Using tokens in CI/CD

### GitHub Actions with OIDC (Recommended)

If your registry supports OpenID Connect, GitHub Actions can
authenticate without storing a token:

<Code
  code={`name: Publish
on: [push]

jobs: publish: runs-on: ubuntu-latest permissions: contents: read
id-token: write # Required for OIDC steps: - uses:
actions/checkout@v4 - uses: vltpkg/setup-vlt@v1 - run: vlt publish`}
title="github-actions.yml" lang="yaml" />

**Advantages:**

- No static tokens to manage or rotate
- Each publish generates a short-lived credential
- Credentials are never stored in secrets
- Automatic credential exchange between GitHub and the registry

<Aside type="note">
  OIDC requires `id-token: write` permission in your job. See
  [Authentication → OIDC](/cli/auth#oidc-openid-connect) for full
  details.
</Aside>

### GitHub Actions with service token

For registries that don't support OIDC, use a stored service token:

<Code
  code={`name: Publish
on: [push]

jobs: publish: runs-on: ubuntu-latest steps: - uses:
actions/checkout@v4 - uses: vltpkg/setup-vlt@v1 - run: vlt publish
env: VLT_TOKEN: \${{ secrets.VLT_PUBLISH_TOKEN }}`}
title="github-actions.yml" lang="yaml" />

### npm with vlt registry

If you prefer npm, configure your `.npmrc` to reference the
environment variable:

<Code
  code={`@your-account:registry=https://registry.vlt.io/your-account/main/
//registry.vlt.io/your-account/main/:_authToken=\${NPM_TOKEN}`}
  title=".npmrc"
  lang="ini"
/>

Then in your GitHub Actions workflow:

<Code
  code={`- run: npm publish
  env:
    NPM_TOKEN: \${{ secrets.VLT_PUBLISH_TOKEN }}`}
  title="github-actions.yml"
  lang="yaml"
/>

## Security best practices

### 1. Use the principle of least privilege

Create tokens with only the permissions they need:

- **Publishing only**: `package:write` (which includes `package:read`)
- **Installing only**: `package:read`
- **Member management**: `member:read` (if needed)

Never grant broader permissions than necessary.

### 2. Set expiration dates

Always set an expiration date when creating a token. Industry-leading
platforms have standardized on the following approach:

| Token Type             | Recommended Expiration | Rationale                                                 |
| ---------------------- | ---------------------- | --------------------------------------------------------- |
| Publishing/Deploy      | 90 days                | High-privilege; frequent rotation reduces exposure window |
| Installation/Read-only | 365 days (1 year)      | Aligns with industry-standard defaults [1][2]             |
| Administrative         | 30-60 days             | Highest privilege; most frequent rotation needed          |

Shorter expiration windows reduce the impact if a token is
compromised. Industry standards recommend shorter lifetimes for
high-value operations [3], though this must be balanced against
operational usability.

### 3. Rotate tokens regularly

Implement a token rotation schedule:

- Quarterly rotation for CI/CD tokens
- Annual rotation for lower-privilege tokens
- Immediate rotation if a token is suspected of being compromised

### 4. Use dedicated tokens per system

Create separate service tokens for different purposes:

- One for publishing (GitHub Actions)
- One for dependency installation (CI/CD)
- One for local development (if needed)

This limits the blast radius if a token is compromised.

### 5. Monitor token usage

The vlt.io dashboard tracks each token's `last_used` timestamp.
Regularly review:

- Tokens that haven't been used recently (consider revoking them)
- Unexpected usage patterns or locations
- Expired tokens that haven't been cleaned up

### 6. Avoid storing tokens in files or commiting to version control

Never commit tokens to version control. Common mistakes:

❌ **Don't do this:**

```json
{
  "token": "vlt_1_abc123..."
}
```

❌ **Or this:**

```bash
export VLT_TOKEN="vlt_1_abc123..."
```

✅ **Do this instead:**

```bash
VLT_TOKEN=${{ secrets.VLT_PUBLISH_TOKEN }} vlt publish
```

### 7. Revoke compromised tokens immediately

If a token is exposed:

1. Go to vlt.io → Account Settings → Tokens
2. Find the token and click **Revoke**
3. Create a new token with the same name
4. Update any references in CI/CD systems
5. Review recent activity logs for any unauthorized access

## Audit and compliance

vlt logs all token lifecycle events for compliance:

- Token creation (creator, timestamp, permissions)
- Token usage (last_used tracking)
- Token revocation (timestamp, reason if provided)

To review your token activity:

1. Navigate to **Account Settings** → **Tokens**
2. Select a token to view its metadata and last usage
3. Check your account's activity logs for security-relevant events

<Aside type="tip">
  If you're on an Enterprise plan, detailed audit logs are available
  in the **Activity** section for full compliance and security
  investigation.
</Aside>

## Troubleshooting

### Token doesn't work in CI/CD

1. Verify the token hasn't expired
2. Confirm the token has `package:write` permission
3. Check that the token is correctly referenced in your workflow (no
   typos in secret name)
4. Ensure the registry URL matches your account's registry endpoint

### "Forbidden" or "Unauthorized" errors

- The token may lack the required permission (`package:write` for
  publishing)
- The creator's account role may restrict the token's capabilities
- The token may have expired

### Token accidentally deleted

Create a new token with the same name and privileges, then update your
CI/CD configuration.

## Summary

- Create dedicated service tokens for each automated system
- Use OIDC when available (no stored tokens needed)
- Store tokens only in secret management systems, never in code
- Set expiration dates and rotate regularly
- Grant only the minimum necessary permissions
- Monitor usage and revoke compromised tokens immediately
- Keep audit logs for compliance and security investigations

For more details on authentication, see [Authentication](/cli/auth)
and [Publishing in CI](/cli/commands/publish#publishing-in-ci).
